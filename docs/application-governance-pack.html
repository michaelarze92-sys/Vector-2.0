1. Business Case & Purpose

1.1 Problem Statement

The Property & SHE Manager role spans ten venues across the UK and Egypt, managing estates, facilities maintenance (via Dalkia), health & safety compliance (via WorkNest), lease administration (via SharePoint), and capital projects — all tracked across multiple disconnected systems:

  • Aurora CAFM — jobs, PPMs, reactive maintenance, statutory compliance
  • WorkNest portal — H&S compliance actions, risk assessments
  • SharePoint — lease documents (files, not derived action dates)
  • Email / Teams — day-to-day communications, approvals, decisions
  • Various spreadsheets — quotes, approvals, weekly reports, flash reports

No single system provides a consolidated daily management view across all of these, and none supports on-site mobile capture during venue inspections.

1.2 What the Apps Do

The Estates App Suite is a management layer on top of existing corporate systems — not a replacement for Aurora, WorkNest, or SharePoint. It provides:

  • Daily triage and chase list — consolidated view of priorities across all venues
  • On-site inspection capture — H&S audits, condition surveys, and contractor quality checks, with photo evidence, usable offline in plant rooms and basements with no signal
  • Capital project tracking — stage-gated project management with RIBA design stages, budget checkpoints, and governance logs
  • Lease notice deadlines — the derived action dates that SharePoint's document store doesn't calculate
  • Board SHE report assembly — future capability to generate the quarterly ECT Board report from aggregated data

1.3 What the Apps Do NOT Do

  • They do not replace Aurora CAFM for job logging, PPM scheduling, or statutory compliance tracking
  • They do not replace WorkNest for formal H&S compliance management
  • They do not store or process customer data, financial transactions, or gaming data
  • They do not connect to any Metropolitan Gaming internal network, server, or database
  • They do not require any credentials, API keys, or authentication

3.2 Key Architectural Decisions

DecisionRationale
Single self-contained HTML files Instant deployment via GitHub Pages. No build server, no dependency management in production. Can be shared as a single file.
No backend / no database Eliminates server infrastructure, hosting costs, database administration, and the entire class of server-side security vulnerabilities. Zero attack surface.
No external network requests All assets (fonts, icons, images) are inlined as base64 or SVG. The apps make zero HTTP requests after initial page load. Critical for offline use in venue plant rooms.
localStorage + IndexedDB for persistence localStorage for structured data (~5MB). IndexedDB for binary data (photos, attachments) which would exceed localStorage quotas. Both are same-origin isolated.
PWA with service workers Enables "Add to Home Screen" installation, offline access, and background cache updates. Each app has its own service worker and manifest for independent installation.
No framework / no bundler Vanilla HTML/CSS/JS only. No React, Vue, Angular, webpack, or npm runtime dependencies. Reduces supply-chain risk to zero and eliminates dependency vulnerabilities entirely.

4. Data Handling & GDPR Statement

4.1 Data Processing Summary

Key principle: All data is processed and stored locally on the user's device. No personal data is transmitted to, collected by, or stored on any external server. The applications have no backend, no analytics, no cookies (from the application), and no third-party data sharing.

4.2 Categories of Data Held

Data CategoryExamplesPersonal Data?Storage Location
Venue/property information Venue names, addresses, sq footage, landlord names, contractor assignments No (business premises data) Browser localStorage on user's device only
Inspection findings Building condition grades, H&S audit results, defect descriptions, photos No (property condition data) Browser localStorage + IndexedDB on user's device only
Issue/risk records Maintenance issues, compliance gaps, RAG severity ratings No (operational data) Browser localStorage on user's device only
Project records Project tasks, budgets, tender records, meeting notes No (project management data) Browser localStorage on user's device only
Individual names Inspector name, action owner, contractor contact, meeting attendees Yes — limited personal data Browser localStorage on user's device only. Never transmitted externally.

4.3 GDPR Assessment

  • Data controller: Metropolitan Gaming (the apps are tools used by an employee in the course of their duties)
  • Data processor: None. No third party processes any data from these apps.
  • Lawful basis: Legitimate interest (property management and H&S compliance record-keeping)
  • Data minimisation: Only operationally necessary data is captured. No customer, gaming, or financial transaction data.
  • Data portability: All apps support full JSON backup export. Inspection findings export as CSV.
  • Right to erasure: Clearing browser data for the relevant domain removes all data immediately.
  • International transfer: No data leaves the user's device. GitHub Pages serves the application code (empty templates) only — no user data is uploaded.
  • DPIA required? Unlikely, given: single user, no systematic monitoring of individuals, no large-scale processing, no sensitive personal data. Recommend formal confirmation from DPO.

4.4 Data Retention & Backup

  • Data persists until the user clears browser storage or uninstalls the PWA
  • All three apps include backup/restore functionality (JSON export/import)
  • The Ledger has an automated backup reminder (configurable, defaults to weekly)
  • Backup files are the user's responsibility to store securely — they may contain names of individuals

5. Security Posture

5.1 Attack Surface Analysis

Summary: The apps have effectively zero network attack surface. There is no backend server, no API endpoint, no database, no authentication system, no session management, and no data transmission to attack.
OWASP Top 10 CategoryApplicable?Assessment
A01: Broken Access ControlNoNo access control exists — single-user, local-only app. No multi-user, no roles.
A02: Cryptographic FailuresNoNo cryptographic operations. HTTPS provided by GitHub Pages (TLS via Let's Encrypt).
A03: InjectionMinimalNo SQL, no server-side processing. DOM manipulation uses textContent where possible. User input is rendered into the user's own browser only.
A04: Insecure DesignNoNo security-critical design decisions — the app is a personal productivity tool.
A05: Security MisconfigurationLowGitHub Pages provides default secure headers. No server to misconfigure.
A06: Vulnerable ComponentsNoZero runtime dependencies. No npm packages, no CDN resources, no third-party libraries.
A07: Auth FailuresNoNo authentication system exists.
A08: Data Integrity FailuresLowService worker updates are user-initiated (toast prompt). No CI/CD pipeline to compromise.
A09: Logging & MonitoringN/ANo server-side logging. Browser console only.
A10: SSRFNoNo server-side requests of any kind.

5.2 Hosting Security (GitHub Pages)

  • HTTPS enforced (TLS 1.2+, certificate managed by GitHub via Let's Encrypt)
  • No custom server configuration possible — static files only
  • GitHub's infrastructure handles DDoS protection and uptime
  • Repository access controlled via GitHub account (currently public — see Section 9)

5.3 Supply Chain Security

  • Zero runtime dependencies. No npm packages are loaded at runtime. No CDN resources.
  • The only development dependency is Playwright (for automated testing) — never shipped to production
  • All assets (fonts, icons, images) are inlined into the HTML at build time — no external fetches
  • No third-party scripts, tracking pixels, analytics, or advertising

5.4 Data at Rest

  • Browser localStorage and IndexedDB are same-origin isolated — only pages served from the exact same domain and path can access the data
  • Data is not encrypted at rest (browser storage is not encrypted by default). Physical device security is the user's responsibility.
  • Recommend: device-level encryption (BitLocker / FileVault / phone encryption) as standard corporate device policy

8. Release & Change Management Process

8.1 Development Workflow

  1. Feature work is developed on a dedicated branch (never directly on main)
  2. Changes are committed with descriptive commit messages explaining the "why"
  3. A pull request is created for review before merging
  4. Automated tests are run and must pass before merge
  5. PR is merged to main branch
  6. GitHub Pages automatically deploys from main within 2-3 minutes
  7. PWA service workers detect the update and prompt the user via an in-app toast notification — the update is not applied automatically to avoid interrupting in-progress work

8.2 Rollback Procedure

Git revert on main branch, push, GitHub Pages redeploys. Full rollback achievable within 5 minutes. All previous versions recoverable from git history.

8.3 Environment Summary

EnvironmentPurposeURL
DevelopmentFeature branches, local testingLocal file:// or localhost
ProductionLive apps via GitHub Pagesmichaelarze92-sys.github.io/*

There is no staging environment. Given the single-user nature and zero-backend architecture, the risk of a bad deploy is limited to one user's UI experience, recoverable by rollback or browser cache clear. A staging environment can be added if the user base expands.
